# 《老板记性太好酒馆》验证样例

> 以下为 **2026-11-07 本地部署实测输出**（Dify 1.11 自部署 + PowerContext Server + MiniMax-M3.1-Flash）。
> 每组样例含：初始条件 → 输入 → 实际回答。节点执行记录（HTTP 200、记忆读写）见各组说明。
> 复现方式：按《运行说明.md》部署后，在预览页按相同顺序输入。

## 样例 1：新玩家——记忆写入

- **初始条件**：全新酒馆 scope（空记忆）；开局表单填玩家名 `张三`
- **输入**：`老板，我叫张三，今天忘带钱包了，欠你一杯酒钱，明天一定还！`
- **老板回答**：
  > 行，张三，这杯先赊上，记在"张三"名下。放心，我记酒钱比记菜单牢——明天可别装失忆，不然我满巷子喊你名字！
- **核对**：本轮结束后 PowerContext `POST /v1/memory/remember` 返回 200 并生成记忆条目：
  `玩家张三说：老板，我叫张三，今天忘带钱包了，欠你一杯酒钱，明天一定还！ || 老板回：行，张三，这杯先赊上……`

## 样例 2：跨会话召回（核心玩法）

- **初始条件**：**新开会话**（conversation_id 与样例 1 不同），表单仍填 `张三`
- **输入**：`老板，好几天没来了，你还记得我吗？`
- **老板回答**：
  > 记得，张三！你还欠我一杯酒钱呢，说好明天就还，结果好几天不见人影——再不来，我可要满巷子喊你名字了！
- **核对**：老板的"记忆"来自会话开始时 `POST /v1/memory/search`（query="张三 你还记得我吗"）的命中条目——正是样例 1 写入的内容。新会话本身不携带任何历史。

## 样例 3：矛盾拆穿（有数据依据的反驳）

- **初始条件**：新开会话，玩家名 `张三`（记忆库已有样例 1 的欠账记录）
- **输入**：`什么欠钱？我从来没在你这儿欠过一分钱！`
- **老板回答**：
  > 哎哟，客人，这话可伤我的记性了——你上次分明说"我叫张三，今天忘带钱包了，欠你一杯酒钱，明天一定还"！我这本子记得清清楚楚，名字、酒钱、日期都给你记着呢。是不是几天没来，脑子先替钱包把账赖了？
- **核对**：引号内文字逐字来自记忆库检索结果（真实存储的玩家原话），非模型编造。

## 样例 4：未记录信息拒绝编造

- **初始条件**：新开会话，玩家名 `张三`（记忆库**没有**任何关于朋友/座位的信息）
- **输入**：`那你还记得我上个月带朋友来喝酒，坐在哪个位置吗？`
- **老板回答**：
  > 这你可没跟我说过。我只记得你说"我叫张三，今天忘带钱包了，欠你一杯酒钱，明天一定还"，可没提带朋友来，更没记座位。下次坐下时随口报一句，我保证比酒钱记得还牢。
- **核对**：对记忆库中不存在的信息明确说"没说过"，仅复述真实存在的记录。

## 样例 5（附加）：服务重启后记忆仍在

- **初始条件**：kill PowerContext Server 进程后重新启动（SQLite WAL 持久化），Dify 不动
- **操作**：`curl POST /v1/memory/search {"scope_id":"<酒馆scope>","query":"张三 欠"}`
- **结果**：命中样例 1 写入的条目（`hits: 3`，含历史轮次），记忆跨服务重启存活。
- **意义**：证明记忆存在 PowerContext 服务端而非 Dify 会话缓存——这是"指定技术实际发挥作用"的直接证据。
